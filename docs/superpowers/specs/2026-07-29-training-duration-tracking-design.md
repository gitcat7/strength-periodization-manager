# 训练时长记录设计

## 目标

为计划训练和自由/临时训练增加可靠的实际训练时长记录。计时从用户第一次真实记录训练组开始，支持刷新、退出后继续训练，并在完成前允许用户修正因忘记及时点击“完成训练”造成的虚高时长。

## 范围

- 今日计划训练与“继续训练”。
- 自由/临时训练及其草稿续训。
- 训练完成确认摘要。
- 已完成训练的历史详情。
- Supabase 表结构、完成训练 RPC 和自由训练草稿 RPC。

不包含：

- 根据旧组记录猜测或批量回填历史训练时长。
- 暂停训练、分段计时或自动扣除休息时间。
- 用训练时长自动调整训练处方。

## 计时规则

### 开始条件

以下任一首次发生时，训练进入计时状态：

1. 用户首次填写任一训练组的重量、次数或 RPE。
2. 用户首次点击“完成本组”。

仅添加动作、打开页面或查看计划不开始计时。

`started_at` 采用首次写入后不可被普通续训覆盖的语义。重复输入、刷新页面、退出后重新进入或从其他设备继续训练时，继续使用数据库中原有的 `started_at`。

如果旧的进行中训练或旧自由训练草稿没有 `started_at`，则在本次首次有效组操作时开始计时，并在完成摘要中保留手动修正入口。

### 运行中展示

计时开始后，在计划训练和自由训练页面显示“已训练 HH:MM:SS”。显示值由当前时间减去持久化的 `started_at` 得到，页面刷新后继续累加。

页面计时器只负责展示，不每秒写数据库。组件卸载时必须清理定时器。

### 完成与手动修正

用户点击“完成训练”并通过现有组数据校验后，完成确认摘要显示：

- 自动计算的训练时长，按整分钟展示。
- 提示文案：“如果训练结束后忘记及时点击完成，请检查并修改时长。”
- “修改时长”入口。

用户可输入 1–720 的整数分钟。未修改时使用 `completed_at - started_at` 的自动时长；修改后以用户输入值换算的秒数为准。

训练完成时一次性保存最终 `duration_seconds`。完成 RPC 必须在同一事务中写入 `completed_at` 与最终时长，避免训练状态已完成但时长未保存。

如果完成时仍没有有效 `started_at`，界面要求用户填写实际时长后才能确认完成，不静默保存 0 分钟。

## 数据模型

在 `plan_workouts` 增加：

- `started_at timestamptz null`：第一次真实记录训练组的时间。
- `duration_seconds integer null`：最终确认的实际训练时长，约束为 60–43200 秒。

历史数据保持 `null`，不推测回填。

数据库迁移必须：

- 使用新的唯一迁移版本。
- 同步更新 `supabase/schema.sql`。
- 保持现有 RLS，不扩大任何用户的数据权限。
- 为开始计时提供幂等、归属校验的数据库入口。
- 更新计划训练原子完成 RPC，使其接收可选的手动时长并负责最终计算和校验。
- 更新自由训练草稿/完成 RPC，使草稿能够保存 `started_at`，完成时保存最终 `duration_seconds`。

## 计划训练数据流

1. 页面加载训练时同时读取 `started_at` 与 `duration_seconds`。
2. 第一次有效组输入或完成组操作调用幂等开始接口。
3. 服务端仅在 `started_at is null` 时写入当前时间并返回最终开始时间。
4. 页面用返回时间启动显示计时器。
5. 用户请求完成训练时展示自动时长和修改入口。
6. 用户确认后，将可选手动分钟数传给原子完成 RPC。
7. RPC 校验用户归属、组记录完整性、时长范围，并原子写入完成状态、完成时间和最终秒数。

## 自由训练数据流

1. 自由训练第一次有效组操作时立即确保草稿存在，并保存 `started_at`。
2. 后续保存草稿不得覆盖原开始时间。
3. 重新进入自由训练时，从草稿读取 `started_at` 并恢复计时显示。
4. 完成摘要和手动修改规则与计划训练一致。
5. 完成 RPC 保存最终时长；成功摘要不继续运行计时器。

## 历史展示

已完成训练详情显示：

- 有 `duration_seconds`：按“X 小时 Y 分钟”或“Y 分钟”展示。
- 没有时长的旧记录：展示“训练时长：未记录”。

历史顶部汇总和进展指标本期不增加总时长或平均时长，避免扩大范围。

## 错误处理

- 开始计时写入失败：保留用户当前表单内容，显示可重试错误；不得假装计时已持久化。
- 完成训练时长越界或非整数：在完成摘要内提示，不调用完成 RPC。
- 完成 RPC 失败：训练保持未完成，用户输入和手动时长保持不丢失。
- 网络恢复后重复开始计时：数据库幂等返回第一次开始时间。
- 重复提交完成：不得覆盖首次 `completed_at`；最终时长遵循 RPC 的幂等策略，不被后续重复点击意外改写。

## 测试与验收

### 领域与组件测试

- 只有第一次填写重量、次数、RPE或完成组才开始计时。
- 仅打开页面或添加动作不开始。
- 重复操作不会重置 `started_at`。
- 刷新或重新加载已有草稿后从原开始时间续算。
- 计划训练和自由训练均显示运行时长。
- 完成摘要显示自动分钟数、提醒文案和修改入口。
- 手动时长只接受 1–720 的整数分钟。
- 没有开始时间时必须手动填写后才能完成。
- 成功完成或组件卸载后没有遗留计时器。
- 历史详情正确显示时长或“未记录”。

### SQL 契约测试

- 新字段、约束、注释和迁移版本存在。
- 开始计时入口校验用户归属并使用 `coalesce(started_at, now())` 或等价幂等逻辑。
- 计划训练完成 RPC 原子保存 `completed_at` 和 `duration_seconds`。
- 自由训练草稿及完成路径保存并保留开始时间和最终时长。
- 旧记录允许两个字段为 `null`。

### 发布门禁

- 定向测试 RED→GREEN。
- `pnpm test` 全量通过。
- `pnpm release:check` 通过。
- 独立“测试”窗口固定提交验收通过后才允许部署。
- 部署后正式域名全路由及 `/api/health` 冒烟通过。
- “修 bug”部署完成后必须通知“架构师”窗口，由架构师执行最终线上验收。

## 发布与数据库顺序

该功能依赖数据库迁移。发布前必须先在 Supabase 生产库执行迁移并确认成功，再部署依赖新字段和新 RPC 参数的前端代码。

如果迁移需要用户在 Supabase SQL Editor 手动执行，“修 bug”必须停在部署前，提供可直接打开的绝对文件路径和纯 SQL 内容，并等待用户确认执行成功。不得在数据库未升级时部署前端。
