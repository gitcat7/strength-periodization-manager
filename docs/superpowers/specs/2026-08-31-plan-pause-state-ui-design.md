# 计划暂停态 UI 重构设计

## 目标

当活动周期处于暂停状态时，计划页应清楚显示暂停事实、恢复影响和唯一正确的恢复入口，避免用户误以为仍可执行当天训练。

## 范围与边界

- 只修改 `ProgramManager` 的暂停状态呈现及组件测试。
- 保持现有 pause/resume event、`openAdjustmentDialog("resume")`、恢复路线、日程预览和伤病确认不变。
- 不改训练算法、Supabase 查询语义、RPC/schema/migration、缓存 key、依赖或非暂停态 UI。
- 暂停页不能出现 `/today` 训练入口、训练录入入口或自动恢复行为。

## 暂停态总览

`pauseState.paused` 时，以橙色暂停态总览替代原“当前周期”主视觉：

- 显示“计划已暂停”和“暂停第 N 天”，其中 N 为 `max(0, daysBetween(effective_date, today)) + 1`。
- 显示计划名称、暂停日期、暂停原因友好标签和预计恢复日期；未填写时显示“未设置恢复日期”。
- 显示固定解释：暂停期间不生成逾期训练、不计入完成率或 Coach 调整；既有训练记录不改写。
- 唯一实心主操作是“恢复训练”，点击继续调用既有 `openAdjustmentDialog("resume")`，并保持 `selectedRoute === null`。
- 次级操作为“查看计划安排”（锚点至只读计划内容）与“修改计划”。预计恢复日期已过时仅提示“恢复日期已过，仍需手动确认恢复”，绝不自动恢复。

## 恢复中心

暂停态下，原“日程调整”卡改名为“恢复中心”：

- 显示已有 `getRecoveryLoadAdvice(daysInterrupted)` 的标题和建议。
- 有待恢复训练时，显示下一节训练名称和 `getWorkoutMeta(name).focus`，说明恢复后会重新计算后续日期。
- 无待恢复训练时，禁用“恢复训练”并显示“当前周期没有待恢复训练日，无法恢复日程。”
- 暂停时不显示“暂停、恢复或多休一天”、`今天多休一天` 或 `暂停计划`。

## 可访问性与响应式

- 主/次级按钮使用现有 `h-11` 或更高高度、`flex-wrap`、`whitespace-nowrap`、`min-w-0`，确保移动端不裁切。
- 使用现有 Lucide `Pause`/`Play` 与色板；不新增依赖。

## 测试策略

组件测试覆盖暂停总览、无/有恢复日期、过期日期不自动恢复、无 pending 行禁用、恢复对话框默认未选路线，以及非暂停态仍有既有训练入口和日程调整控件。测试使用现有 Supabase mock，验证 DOM 和既有恢复对话框，而非替代 RPC 行为。
