# 力训周期管家任务导向移动端体验优化设计

日期：2026-07-30  
状态：已确认  
适用范围：计划、历史、今日训练、首页、进展、设置及全局视觉规范

## 1. 背景与目标

当前产品功能闭环已经形成，但核心页面的信息层级、操作密度和组件样式仍不够统一。计划与历史页面较长，浏览状态和编辑状态混在一起；今日训练、首页和进展页虽然可用，但主要任务不够突出。

本轮不改变训练算法、计划生成规则或数据库结构，也不进行品牌重做。目标是在保留现有绿色、白底、卡片化风格的前提下：

- 让每个页面只突出一个当前最重要的任务；
- 降低移动端滚动长度和误操作风险；
- 统一按钮、卡片、状态、输入和反馈的视觉语义；
- 保证训练中的高频操作可单手完成；
- 为 375px、390px、430px 手机宽度建立稳定验收基线。

## 2. 设计原则

1. **任务优先**：首屏先回答“用户现在应该做什么”。
2. **浏览与编辑分离**：默认只读，明确进入编辑状态后才显示可修改控件。
3. **渐进披露**：摘要优先，详情按循环、周、动作或训练记录展开。
4. **一个主要操作**：同一操作区只保留一个视觉主按钮。
5. **训练中可触达**：完成组、休息计时和完成训练必须靠近拇指区域。
6. **科学信息不隐藏**：目标、训练方向、完成率、RPE、建议依据等关键训练信息保持可见。
7. **兼容现有数据**：旧计划、自由训练、休息日和历史记录继续只读兼容。

## 3. 方案选择

采用“任务导向优化”，不采用仅换颜色的表面美化，也不采用高风险的整体重构。

- 保留现有路由、数据接口和训练领域逻辑；
- 重组页面内信息层级；
- 提取有限的共享 UI 原语；
- 分页面、分批发布，每批独立回归。

## 4. 页面设计

### 4.1 计划页面

#### 已有计划用户

首屏展示“当前周期概览”，内容包括：

- 计划名称与日期范围；
- 当前第几周、当前循环；
- 下一训练日、训练方向和状态；
- 唯一主操作“开始训练”或“继续训练”。

“调整计划”“按当前参数重新生成”“更新体重、饮食与恢复”统一收进“计划管理”区。计划管理默认收起，重新生成继续使用影响范围说明和二次确认。

计划内容按以下层级渐进展开：

1. 默认展开当前周；
2. 当前周默认展开当前训练循环；
3. 用户可展开其他循环；
4. 用户可展开其他周；
5. 提供“全部展开”和“全部收起”。

Fitness Coach 建议位于周期概览之后、计划明细之前。每条建议必须展示来源训练、当前重量、建议重量、影响范围和应用/忽略操作。

#### 无计划用户

保留创建计划入口，但不同时展示计划浏览组件。创建流程仍使用现有参数校验和训练结构选择。

### 4.2 历史页面

月历继续作为主要日期入口。选择日期后先展示当天摘要：

- 训练名称与类型；
- 训练时长；
- 完成组数与完成率；
- 总训练量；
- 平均 RPE；
- 各动作最佳组。

训练记录默认只读。动作和每组数据在“查看详情”后展开；只有点击“修改记录”后，重量、次数、RPE、完成状态和时长才进入编辑模式。

编辑状态要求：

- 明确显示“正在修改历史记录”；
- 提供“保存修改”和“取消”；
- 保存成功后退出编辑态；
- 告知用户 Coach 待处理建议已重新计算；
- 保存失败时保留当前输入，不静默丢失。

### 4.3 今日训练

顶部增加紧凑进度信息：

- 已完成组数/计划组数；
- 当前训练方向；
- 训练已持续时长。

动作以独立区块展示：

- 当前动作默认展开；
- 已完成动作自动折叠为摘要；
- 未开始动作保持紧凑；
- 用户仍可手动展开任意动作。

每组输入继续支持重量、次数、RPE 和完成按钮。移动端必须完整显示 `22.5` 等小数值；完成按钮触控尺寸不得小于 44px。

完成一组后，休息提示以不遮挡下一组输入的底部浮层出现。页面底部只保留一个主要“完成训练”操作；未满足完成条件时显示可执行的缺失项，而不是笼统报错。

完成训练后显示摘要与训练时长，并允许按现有规则修正时长。

### 4.4 首页

首页保持工作台定位：

- 顶部统计压缩为紧凑数据条；
- “下一次训练”成为首屏唯一视觉重点；
- “继续训练”为主操作；
- “自由训练”为次级文字或描边入口；
- 最近训练、Coach 建议、PR 目标只展示摘要和跳转入口。

不在首页复制计划页、历史页或进展页的完整数据。

### 4.5 进展页面

提供 `4周 / 8周 / 12周`时间范围切换，默认 8 周。

周训练量应显示：

- 周总量；
- 完成组数/计划组数；
- 与上一周期的变化。

主项 e1RM 图表应显示日期、数值、最佳值和区间变化。趋势卡先给出自然语言结论，再展示图表，例如：

- 训练量连续两周上升；
- 卧推 e1RM 较区间起点提高 3.5kg；
- 完成率下降，建议先稳定训练执行。

趋势文案只描述数据，不给出医疗诊断。

### 4.6 设置页面

设置按以下分组呈现：

1. 账号；
2. 训练偏好；
3. 数据管理；
4. 高级功能。

Agent 授权、诊断和低频维护入口放入默认收起的高级功能。退出登录、撤销授权等高影响操作与普通设置保持足够视觉距离，并保留确认。

## 5. 全局组件与视觉规范

提取或统一以下 UI 原语，但不建设庞大组件库：

- `PageHeader`
- `SectionHeader`
- `PrimaryButton`、`SecondaryButton`、`DangerButton`
- `MetricStrip`
- `StatusPill`
- `ActionCard`
- `DisclosureCard`
- `NumberField`
- `InlineNotice`
- `LoadingSkeleton`
- `EmptyState`

统一要求：

- 页面左右边距在手机端保持一致；
- 卡片圆角、边框、背景和阴影使用有限档位；
- 数字使用等宽数字样式并右对齐；
- 主按钮高度至少 44px；
- 错误、警告、完成、恢复、强度和普通状态使用稳定语义色；
- 支持安全区域和底部导航；
- 禁止横向滚动；
- 尊重 `prefers-reduced-motion`。

## 6. 状态与错误处理

每个核心页面均覆盖：

- 首次加载骨架；
- 无数据空状态；
- 可恢复错误与重试；
- 保存中防止重复提交；
- 保存成功的就地反馈；
- 网络失败时保留未提交输入；
- 已完成或只读数据的明确状态。

不使用只有 `TypeError`、`Load failed` 等技术性提示的用户文案。

## 7. 实施批次

严格按以下顺序，每批单独实现、测试、部署和验收：

1. 计划页面；
2. 历史页面；
3. 今日训练；
4. 首页与进展页面；
5. 设置页面与全局视觉收口。

后续批次不得以未完成前序批次为前提夹带发布。

## 8. 验收标准

### 通用

- 375px、390px、430px 下无横向溢出；
- 所有数字输入完整显示小数；
- 主要触控目标不小于 44px；
- 键盘焦点、标签和按钮名称可访问；
- 加载、空数据、错误、成功状态均有明确反馈；
- 底部导航和固定操作不互相遮挡；
- TypeScript、生产构建、自动测试和路由 smoke 全部通过。

### 页面专项

- 已有计划用户进入计划页时不显示首次生成表单；
- 计划默认只展开当前周和当前循环；
- 历史记录默认只读，编辑必须显式进入；
- 今日训练能一眼看到完成进度和当前动作；
- 首页首屏只有一个主训练操作；
- 进展页切换时间范围后指标和结论同步变化；
- 高级设置默认不会干扰普通用户。

## 9. 工作流

每个批次遵循固定门禁：

1. “修 bug”窗口基于固定提交实现；
2. 本地测试和发布检查通过；
3. “测试”窗口独立验证并明确回复“验证通过”；
4. 验证通过后部署固定提交；
5. 部署完成后通知架构验收窗口；
6. 架构验收生产页面、健康接口和关键流程后关闭批次。

本轮预计不需要数据库迁移。若实现中出现必须新增持久化字段的需求，应停止该批次并单独设计数据库变更，不得把未经确认的 SQL 混入视觉优化。
